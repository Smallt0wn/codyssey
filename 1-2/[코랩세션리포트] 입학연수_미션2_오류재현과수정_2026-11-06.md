# 코랩 세션 리포트 - 오류를 재현하고, 본 대로 물어서 고치기

오늘의 학습활동에서는 **기획서와 다르게 동작하는 영화 티어리스트**에서 오류를 직접 재현하고, AI에게 본 장면을 전해 원인을 물으며 오류를 수정했습니다. 같은 파일에서 출발했지만, **어떤 오류를 찾았고 AI에게 어떻게 질문했는지, 어떤 원인을 답변으로 받았는지는 사람마다 다릅니다. 그렇다면 다른 사람은 같은 오류를 어떻게 설명해서 원인을 찾아냈을까요?**

다른 사람의 설명에서 내가 놓친 장면이나 행동 순서를 발견할 수도 있고, 같은 오류에 AI가 다른 원인을 말한 이유를 알아볼 수도 있습니다. 실제 업무에서도 동료들과 오류를 찾고 수정한 과정을 공유하고 비교하며 서로의 접근 방식에서 배우는 과정이 중요합니다.

**코랩 세션**은 같은 학습활동을 마친 동료와 1:1로 각자의 작업 과정과 결과물을 공유하고 이야기하는 시간입니다. 이 리포트는 세션 전과 세션 중, 세션 후에 걸쳐 작성하며, 자신의 작업을 설명하고 이해하지 못한 부분을 동료와 함께 확인한 뒤 서로의 접근 방식과 결과를 비교합니다.

각 항목을 순서대로 작성하고, 작성하지 못한 항목이 있다면 그 이유를 기록합니다.

7장 동료평가는 2-2 진행 체크리스트의 항목을 동료가 했는지 체크하는 평가 항목입니다. 7장 이외의 항목은 세션 뒤에 작성을 마칩니다. 작성을 마친 내용은 산출물로 제출하며, 제출 방법은 운영 안내를 따릅니다.

## 1장. 개요

이번 코랩 세션에서는 각자 찾은 오류와 수정 과정을 공유하고, 같은 파일에서 발견한 오류가 서로 다른 설명과 수정으로 이어진 과정을 살펴봅니다.

AI와 함께 오류를 찾고 수정하는 과정에서는 AI가 말한 원인을 받아들이기도 하고, 직접 확인한 결과에 따라 다시 묻거나 수정 범위를 줄이기도 했을 것입니다. 하지만 수정된 파일만 보면 **무엇을 직접 봤고 무엇을 짐작했는지, 어떤 원인을 내가 확인했고 어떤 부분에서 AI의 도움을 받았는지** 명확하게 설명하기 어려울 수 있습니다. 이번 세션에서는 자신의 작업 과정을 돌아보며 **AI에게 무엇을 전했고, 그 원인을 받아들인 이유는 무엇인지** 설명하고, 이러한 판단이 실제 수정 결과에 어떻게 반영되었는지 동료와 함께 확인합니다.

또한 **다른 사람은 같은 오류를 AI에게 어떻게 설명했고, 어떤 답변을 바탕으로 무엇을 수정했는지** 살펴봅니다. 같은 오류를 만나더라도 서로 다른 순서로 재현하고 다른 원인을 찾을 수 있고, 그 이유를 이해하는 과정에서 내가 놓친 장면이나 확인 방법을 발견할 수도 있습니다. 서로의 고민과 해결 과정을 공유하며, 혼자 작업할 때는 발견하지 못했던 새로운 방법과 가능성을 찾아봅니다.

### 2-1. 결과물 요약

개발자도 작업을 진행하면서 어떤 부분을 변경했는지 기록합니다. 이 때 사용하는 도구가 Git이며, 파일의 변경 내용을 저장하는 단위를 **커밋(commit)**이라고 합니다. 커밋에는 보통 무엇을 변경했는지 알 수 있도록 간단한 메시지를 남깁니다. (Git은 파일의 변경 이력을 관리하는 버전 관리 시스템이고, GitHub는 그 기록을 외부 저장소에 올려 두는 서비스입니다.)

`영화_수정전.html`을 덮어쓰지 않고 고친 파일을 `영화_수정1.html`처럼 새 이름으로 남긴 것도 이런 개발 습관과 연결됩니다. 고친 오류 하나를 선택해, 무엇을 바꿨고 왜 바꿨는지 드러나는 커밋 메시지로 다시 작성합니다. 아직 고치지 못했다면 `영화_수정전.html`을 남긴 일이나 고치려고 한 내용으로 대신합니다.

예를 들어 '이동 수정' 대신 '제목에 띄어쓰기가 있는 영화도 누르거나 끌어서 옮겨지도록 고침 (기획서 완성 기준: 처음 영화 8개와 새로 추가한 영화 모두 옮길 수 있음)'처럼 작성할 수 있습니다.

본과정의 AI 활용 학습 단계에서는 Git을 사용해 실제로 커밋을 남기게 됩니다.

| 항목 | 내용 |
|---|---|
| 선택 항목 (수정 사항이 없으면 대체 작업) | 띄어쓰기가 있는 제목의 영화가 옮겨지지 않는 오류 수정 |
| 커밋 메시지 (작업 내용과 이유) | [1-2] 제목에 띄어쓰기가 있는 영화도 누르거나 끌어서 옮겨지도록 카드 이름표를 제목 전체로 붙이게 고침 (기획서 완성 기준: 처음 영화 8개와 새로 추가한 영화 모두 옮길 수 있음) |

## 3장. 지시와 구성 대조

### 진행 방법

1. **살펴보기** - 각자 선택해 온 메시지를 공유하고, 내가 전한 장면과 AI가 말한 원인을 나란히 둡니다.
2. **이야기 나누기** - 전한 문장에서 본 것은 어디까지였고 추측은 어디부터였는지 둘이 서로 짚어 줍니다. 같은 오류에 AI가 두 사람에게 다른 원인을 말했다면 전한 문장이 어떻게 달랐는지 비교합니다.
3. **수정 과정 살펴보기** - 한 번에 몇 가지 수정을 요청했는지, 수정한 뒤 다른 기능이 깨졌는지 서로 묻습니다.
4. **커밋 메시지 서로 읽기** - 2-1에서 작성한 커밋 메시지를 동료와 바꿔 읽고, 어떤 표현이 작업 내용을 더 명확하게 전달하는지 비교합니다.

어디서부터 시작할지 막막하다면, 2-3에서 선택해 온 메시지 하나를 살펴보고 그 안에서 본 것과 추측을 나눠 기록합니다.

## 4장. 구성 분석

### 진행 방법

1. **살펴보기** - `영화_수정전.html`과 `영화_수정1.html`을 브라우저에서 나란히 열고, 오류가 났던 행동을 두 파일에서 똑같이 반복한 뒤 AI의 수정 설명에서 바꿨다고 한 곳의 이름을 찾습니다.
2. **이야기 나누기** - 오류가 생긴 곳과 수정한 곳이 HTML에서 무슨 일을 맡는 부분인지, 왜 그 부분에서 오류가 났는지 이야기합니다.

진행이 어렵다면 다음 순서를 따라갑니다.
1. 수정 설명에 바꾼 곳의 이름이 없거나 알아보기 어려우면, AI에게 "수정 전과 수정 후에 바뀐 부분이 HTML의 어디인지, 각각 무슨 일을 맡는지 이름과 한 문장으로 알려 줘"라고 질문합니다.
2. 코드를 읽을 필요 없이 이름과 하는 일만 기록합니다.

### 4-1. 수정 위치

| 수정 부분 (AI가 알려 준 이름) | 역할 (한 문장) | 오류와의 관계 (추정) |
|---|---|---|
| 예시 영화 카드를 만드는 부분 | 영화마다 카드를 만들고 어느 영화인지 알아볼 이름표를 붙인다 | 이름표에서 띄어쓰기 뒤가 빠져서 옮길 때 영화를 찾지 못한 것 같다 |
| 영화 카드를 만드는 부분 (`card`) | 영화마다 카드를 만들고 어느 영화인지 알아볼 이름표(`data-id`)를 붙인다 | 이름표를 따옴표 없이 붙여서 띄어쓰기 앞에서 끊겼다. 수정 후에는 카드를 만든 뒤 이름표를 제목 전체로 따로 넣는다 |
| 영화를 옮기는 부분 (`move`) - 수정하지 않음 | 카드의 이름표로 저장된 영화 목록에서 영화를 찾아 칸을 바꾼다 | 이 부분은 문제가 없었지만 끊긴 이름표로 찾았기 때문에 영화를 못 찾거나 '토이'처럼 다른 영화를 찾았다 |

### 4-2. 오류와 설계 의도

아래 질문 중 해당하는 것을 선택해 동료와 이야기합니다. 정확한 이유를 몰라도 자신의 생각을 바탕으로 이야기해 봅니다.

- 어떤 영화는 옮겨지고 어떤 영화는 옮겨지지 않는 오류는 왜 생길까요? 화면이 카드마다 어느 영화인지 어떻게 알아보는지 AI에게 물어보고 이야기합니다.
- 띄어쓰기가 있는 제목은 추가하지 못하게 막아야 할까요, 띄어쓰기가 있어도 옮겨지게 고쳐야 할까요?
- 같은 행동을 한 번 더 했을 때 결과가 달랐던 적이 있나요? 있다면 무엇이 남아 있었기 때문일까요?
- '처음으로' 버튼은 무엇을 지우고 무엇을 남겨야 할까요?
- 하나를 고쳤는데 다른 기능이 깨졌다면, 두 기능이 무엇을 함께 사용하고 있었을까요?

| | 조사 내용 |
|:-:|---|
| 1 | 화면은 카드에 붙은 이름표로 어느 영화인지 알아본다. 누르기와 끌어 놓기가 모두 이 이름표를 쓰기 때문에, 이름표가 끊긴 띄어쓰기 제목만 두 방법 모두 실패했다. 띄어쓰기가 없는 제목은 이름표가 온전해서 문제가 드러나지 않았다. |
| 2 | 실제 영화 제목은 띄어쓰기가 있는 경우가 많아서 추가를 막는 건 사용자에게 불편하다. 띄어쓰기가 있어도 옮겨지게 고치는 게 맞다고 판단했다. |
| 3 | 배치가 브라우저에 저장되기 때문에 '처음으로'를 먼저 누르지 않으면 앞 시험에서 옮긴 결과가 남아 섞일 수 있었다. 그래서 시험마다 '처음으로'를 먼저 눌렀다. |

### 4-3. 안전 점검

AI가 고쳤다고 말하는 것과 실제로 고쳐진 것은 다릅니다.

| 점검 항목 | 점검 결과 |
|---|---|
| 같은 행동을 두 번 해서 매번 같은 결과가 나오는지 확인했나 | 수정 전과 수정 후 모두 같은 시험을 2번씩 했고 두 번 다 결과가 같았다. |
| `영화_수정1.html`을 열고 '처음으로'를 먼저 눌렀나. 누르지 않았다면 앞 시험의 기록이 결과에 섞였을 수 있나 | 눌렀다. 시험마다 '처음으로'를 먼저 눌러 앞 시험의 기록이 섞이지 않게 했다. |
| AI가 말한 원인을 직접 확인했나, 그대로 믿었나 | Console로 카드 이름표를 출력해 띄어쓰기 앞에서 끊긴 것을 직접 확인한 뒤 수정을 요청했다. |
| 고친 뒤 원래 되던 영화도 옮겨 보고, 다시 열기와 '처음으로'를 다시 해 봤나. 깨진 기능이 있었나 | 원래 되던 5개와 '괴물'도 옮겨 봤고, 새로고침과 '처음으로'도 다시 했다. 깨진 기능은 없었다. |
| `영화_수정전.html`이 남아 있나. 수정이 잘못되면 어디서 다시 시작하나 | 그대로 남아 있다. 수정이 잘못되면 `영화_수정전.html`에서 다시 시작한다. |
| 대화 공유 링크를 만들기 전에 대화에 이름 · 연락처 같은 개인정보가 없는지 확인했나 | 확인했다. 대화에 이름, 연락처 같은 개인정보가 없다. |
| 동료와 가장 달랐던 확인 항목과 그 차이 (5-1에 적었으면 그 행을 가리킵니다) | --- |

### 4-4. 오류 설명 재작성

AI에게 처음 전한 설명 가운데 원인을 좁히기 어려운 문장을 선택해 다시 씁니다. 오류가 생기는 경우와 생기지 않는 경우의 차이가 포함되면 잘 쓴 문장입니다.

| 최초 설명 | 수정 설명 | 수정 이유 |
|---|---|---|
| 예시 "어떤 카드는 안 옮겨져요" | "제목에 띄어쓰기가 있는 영화만, 누르기와 끌어 놓기 둘 다 안 옮겨져요" | 되는 경우와 안 되는 경우의 차이까지 전해야 AI가 원인을 좁힐 수 있어서 |
| "센과 치히로의 행방불명, 어벤져스: 엔드게임, 토이 스토리가 안 옮겨져요" | "제목에 띄어쓰기가 있는 영화만 누르기와 끌어 놓기 둘 다 안 옮겨지고, 띄어쓰기 앞부분과 같은 제목이 있으면 그 영화가 대신 옮겨져요" | 영화 이름만 나열하면 영화마다 따로 문제로 볼 수 있어서, 공통점과 '토이'처럼 엉뚱하게 옮겨지는 경우까지 같이 전해야 했다 |

## 5장. 동료 작업 비교

### 진행 방법

1. **살펴보기** - 같은 파일에서 출발했으므로 동료가 좁혀서 적은 한 문장을 내 문장과 나란히 놓습니다.

2. **이야기 나누기** - 누가 어떤 오류를 찾았고 누가 놓쳤는지 비교합니다. 같은 오류를 어떻게 다르게 고쳤는지, 그 차이가 다음 수정에 어떤 영향을 줄지 이야기합니다.

출발한 파일이 같아도 찾는 순서와 고치는 방법은 다를 수 있습니다. 이야기를 시작하기 어렵다면 다음 항목을 비교해 봅니다.

- **되는 영화와 안 되는 영화의 차이를 찾았나요?**

	- 안 되는 영화의 공통점을 어떻게 떠올렸고, 짐작을 확인하려고 어떤 제목을 추가했는지 비교합니다.

- **같은 오류에 AI가 말한 원인이 같았나요?**

	- 사용한 AI와 전한 문장이 어떻게 달랐는지 비교합니다.

- **수정한 뒤 다른 기능이 깨졌을 때 어떻게 했나요?**

	- `영화_수정전.html`로 돌아가 범위를 줄였는지, `영화_수정1.html`에서 계속 수정했는지 비교합니다.

### 5-1. 구현 차이

## 6장. 개선 계획

### 6-1. 회고

| 항목 | 내용 |
|---|---|
| 조사 중 예상 외 발견 | '토이'를 추가하면 '토이 스토리'가 안 옮겨지는 게 아니라 '토이'가 대신 옮겨졌다. 오류가 '안 되는 것'뿐 아니라 '엉뚱하게 되는 것'으로도 나타날 수 있다는 걸 알았다. |
| 반복 작업의 불편 사항 | 시험할 때마다 '처음으로'를 누르고 영화 8개와 추가한 영화를 누르기와 끌어 놓기로 2번씩 옮겨야 해서 시간이 오래 걸렸다. |
| 다음 오류 발생 시 우선 전달 사항 | 되는 경우와 안 되는 경우의 차이, 그리고 짐작을 확인하려고 추가해 본 결과를 같이 전하겠다. |

| | 수정 사항 |

| 2 | 동료평가에서 체크되지 않은 항목이 있으면 그 항목을 보완해 다시 평가받는다. |

### 6-3. 유지 결정

고치지 않기로 한 것을 적는 칸은 고칠 것만큼 중요합니다. 그대로 두기로 한 이유가 내가 내린 판단의 기록으로 남습니다.

| 유지 항목 | 유지 사유 |
| ----------- | --------- |
| 카드 제목을 HTML 글자로 넣는 방식 | 제목에 `<` 같은 기호가 들어가면 화면이 깨질 수 있지만, 이번에는 띄어쓰기 문제만 고치기로 해서 그대로 뒀다. |
| '처음으로'가 추가한 영화까지 지우는 동작 | 기획서에 '처음 영화 목록과 배치로 돌아간다'고 적혀 있어 맞는 동작이라고 판단했다. |

### 6-4. 미해결 사항

미해결 사항을 기록해 두면 다음번에 그 부분부터 살펴볼 수 있습니다.

| 미해결 항목 | 막힌 지점 |
| -------------- | ------- |
| 따옴표 없는 이름표가 띄어쓰기에서 끊기는 이유 | 끊긴 결과는 직접 확인했지만 HTML 규칙 자체는 아직 정확히 설명하지 못한다. |
| 동료 작업과의 차이 | 코랩 세션 전이라 동료의 수정 파일과 기록을 아직 확인하지 못했다. |

## 7장. 동료평가

세션에서 동료의 파일과 기록을 직접 엽니다. 2-2 진행 체크리스트의 항목 가운데 동료가 한 것에 체크합니다. 모든 항목에 체크되면 PASS입니다. 내가 받은 평가에서 체크되지 않은 항목이 있다면 그 항목을 고쳐 다시 평가받습니다. 고칠 내용은 6-2 수정 계획에도 적습니다.

- [ ] `영화_수정전.html`을 덮어쓰지 않고 보관하기
- [ ] '처음으로'를 누른 뒤 `기획서.md`의 완성 기준을 하나씩 해 보기
- [ ] 영화 8개를 하나도 빼지 않고 옮겨 보기
- [ ] 같은 행동을 한 번 더 해 매번 같은 결과가 나오는지 확인하기
- [ ] 되는 영화와 안 되는 영화의 차이 찾기
- [ ] 누르기와 끌어 놓기를 모두 해 보기
- [ ] 짐작을 확인할 제목을 추가해 옮겨 보기
- [ ] 좁힌 내용을 한 문장으로 적기
- [ ] 고치기 전에 원인 후보와 확인 방법부터 묻기
- [ ] AI가 알려 준 확인 방법을 직접 해 보기
- [ ] 그 문제만 고치게 하기
- [ ] `영화_수정1.html`을 열어 '처음으로'를 먼저 누르고, 안 됐던 영화와 원래 되던 영화를 다시 옮겨 보기
